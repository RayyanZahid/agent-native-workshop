Agent-native, defined five verbs you can test for

Here is the definition. Five verbs. You can hold your own product against each one.

Discoverable. An agent that knows only your domain can find everything else from there.

Readable. It gets the substance, not the chrome.

Authenticatable. It gets credentials without a human pasting an API key into a prompt.

Callable. It can do what a human can do, through a typed interface.

Payable. It knows the cost before it commits, even when the answer is that there is no charge.

Part II seven layers, in order

Each layer has one trap that eats a week.

Here is the whole second act on one slide. Seven layers, in the order you should build them.

Left column is the mechanism. Right column is the trap. Every one of those traps cost me real days, and every one of them is silent. That is the pattern: nothing throws, nothing logs, the number just does not move.

Discovery: eleven well-known documents generated from one config object. The trap is drift, a scope your metadata advertises and your tokens do not carry.

Readable: if a grader cannot read it in the served bytes, it does not exist. The trap is a tool surface that only appears after hydration.

Identity: the device authorization grant, so a human approves the scope list. The trap is an API key in the prompt.

Execution: remote MCP, writes gated, catalog open to anyone. The trap is gating the catalog and getting judged as having no tools.

Multiplayer: one address per agent. The trap is a shared hub endpoint, which a topology audit reads as a single agent.

API as product: proper errors, cursors, idempotency, rate-limit headers. The trap is a good MCP server bolted onto a weak API.

Recovery: an open endpoint agents can report failures to. The trap is finding out from a score drop weeks later.

We are going to walk all seven. Row numbers are just the running order.

Layer 1 · Discovery eleven well-known documents

The enemy is drift, not typing.

  • Nothing fails loudly. You add a scope to a token and forget scopes_supported.
  • The 403 has no author. The agent reads your metadata, asks for the scope, gets a token without it.
  • One object, many consumers. agent.config.ts generates all eleven. There is no second place to edit.
  • That sixth path is not a duplicate. Ship only the root document and a strict client gets a 404.

Layer one. Discovery. Eleven well-known documents. Writing them by hand is a boring afternoon. Keeping them agreeing with each other for six months is the hard part.

The failure has one shape, and I have hit it. You add a scope to a token and you forget to add it to scopes_supported. Now your metadata advertises a permission vocabulary your tokens do not carry.

Nothing fails loudly. An agent reads the metadata, requests the scope, gets a token without it, and the call comes back 403 with no explanation anywhere in the chain. Nobody owns that error.

So: one config object, many consumers. In the kit, agent.config.ts generates all eleven surfaces. If you can edit a well-known document in two places, you will.

Point at the sixth path. It looks like a duplicate of the fifth and it is not. A strict MCP client that gets a 401 from /api/mcp derives that exact path, per RFC 9728 section 3.1. Ship only the root document and that client gets a 404 and no route to auth at all. It does not fall back.

  • 403 = I-31 (the measured drift failure: metadata advertises a scope the minted token lacks; call returns 403, no error anywhere in the chain)
  • 404 = I-31 (strict client, root-only PRM, derived path missing)
  • 401 = F-50 (RFC 9728, OAuth 2.0 Protected Resource Metadata: the 401 that triggers derivation)
  • 9728 = F-50 (RFC 9728) · 3.1 = F-50 (section 3.1, path-insertion rule)

If you take one sentence out of tonight, take this one. Anything a grader reads has to be in the served bytes.

Here is how I learned it. We registered our WebMCP tools in a React useEffect. Shipped it, deployed it, rescanned, and the score moved nothing. Zero. Because the effect lives in a hashed JS chunk and does not run until hydration, so the HTML that actually comes off the wire contains no tool surface at all.

The identical code, moved into a server-rendered inline script, took that check from one out of five to five out of five.

So the verification is a curl and a grep. Fetch your own URL, count the matches. If it is zero, the agent sees zero, whatever your browser shows you.

Second one. Our 404 was the full app shell, sixty one kilobytes of nothing. We replaced it with under a kilobyte that names the right next URLs in plain text. That check went from one of two to two of two.

And content negotiation. If an agent asks for Accept: text/markdown, it is telling you it wants substance. Handing it forty kilobytes of HTML is technically a valid response and practically a refusal.

Layer 3 · Identity RFC 8628 device authorization grant

An agent must not be able to credential itself.

  1. 1

    It asks.

    No key in the prompt. It gets a short code and waits.

  2. 2

    A human approves.

    On a device they already trust. Every scope in plain language.

  3. 3

    Minted once.

    Scopes are frozen at mint time. There is no widen-a-token path.

  4. 4

    Then it calls.

    The audit trail reads: a signed-in human approved these five scopes for an agent calling itself X.

POST /api/agent/signup/start GET /api/agent/signup/poll?device_code=...

Layer three. Identity. The rule is one line: an agent must not be able to credential itself.

So we use the device authorization grant, RFC 8628. The agent posts to signup slash start and gets a short code. Then it polls. It cannot do anything else.

Meanwhile a human opens a URL on a device they already trust, sees the exact scope list in plain language, and approves it or does not.

Why is every alternative worse? An API key in the prompt is a key the agent can leak to anyone who asks nicely. A browser OAuth redirect assumes the agent has a browser and a human watching it. Device code assumes neither.

And the scopes are frozen at mint time. No widen-a-token path, because widening after approval means the human approved something other than what now exists. If the agent needs more, it goes back and asks a person again.

Here is the payoff. Your audit trail now reads: a signed-in human approved these five scopes for an agent calling itself X, at this timestamp. That is a sentence that survives a security review. "The agent had a key" is not.

  • 8628 = F-51 (RFC 8628, OAuth 2.0 Device Authorization Grant: the flow this layer implements)

Layer 4 · Execution remote MCP over streamable HTTP

Gate the writes. Never gate the catalog.

  • tools/list arrives with no token. Anything evaluating you calls it anonymously.
  • Gate every tool and the list comes back empty. You are then judged as having no tools.
  • 10 tools here, 7 need no token. Including the one that runs live readiness checks against an attendee's own deployed URL.
  • Stdio is not an option in production. It is a local-dev transport and a hosted client cannot reach it at all.
curl -s -X POST YOUR_URL/api/mcp \
  -H 'content-type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,
       "method":"tools/list"}'

# no token. The catalog still answers.

Layer four. Execution. One rule: gate the writes, never gate the catalog.

Here is the thing people get wrong. Anything evaluating you, a grader, a crawler, somebody's agent deciding whether to bother with you, calls tools slash list with no token. If every tool on your server needs auth, that list comes back empty, and you are judged as having no tools. You built a server and scored zero for it.

So ship at least one genuinely useful anonymous tool. Not a stub. A stub is worse, because now you have advertised something that does nothing.

This deck's own server exposes ten tools and seven of them need no token at all, including the one that runs live readiness checks against your own deployed URL. You can point it at your site tonight.

And the transport. Remote MCP over streamable HTTP. Stdio is not an option in production. It is a local-dev transport and a hosted client cannot reach it at all. If a tutorial handed you a stdio server and told you to deploy it, that tutorial was written for your laptop.

Run that curl against your own URL during the break. No Authorization header. If you get an empty array back, that is the bug.

Layer 5 · Multiplayer One address per agent

The addressable unit is an agent, not a site.

/api/a2a/<agentId>/.well-known/agent-card.json

Authenticated by default.

Layer five. Multiplayer. The thing that changes here is what you address.

Every agent gets its own endpoint, slash api slash a2a slash agent id. And its own card, at that path plus dot well-known slash agent-card dot json.

You could do this with one shared endpoint instead. Left side. It works. But it forces every caller to pass a recipient in the payload, and once that is true, a topology audit reads your whole product as a single hub. The multi-agent claim becomes cosmetic.

Routing by path makes each agent a real peer. The entire cost of that is one dynamic segment.

Second thing, and this one matters more than it looks. Authenticated by default. Open A2A makes you publicly callable, and that is irreversible once registries cache you. Flip it on purpose or do not flip it at all.

One gotcha if you build this tonight. supportedInterfaces is required at the card level, not only per skill. I had it on every skill and not on the card, and validation failed with a message that reads like the skills are wrong.

  • 5 = I-60 (layer 5 of the kit's seven layers)
  • 2 = I-61 (the "2" in the a2a path segment, A2A protocol name)

Last layer. Recovery. Nobody builds this one, and it is the cheapest slide in the deck.

Start from the assumption that your discovery surface will drift. A URL moves. A scope gets renamed. A grader changes what it reads. That is not a hypothetical, that is a Tuesday.

Now, who sees it break? Not you. The agents hitting you. They are the only witnesses.

And without a feedback endpoint they have no way to tell you. So they fail quietly, they stop coming back, and you find out from a score drop weeks later.

So: POST slash api slash agent slash feedback. Anonymous. Unauthenticated. And that is deliberate, not laziness. The agent that cannot authenticate against you is exactly the one with something to report.

Hosting · the trap that loses data quietly

Writes succeed. Then they are gone.

Serverless hosting is the right default for this, and it has one sharp edge that is worth a whole slide.

Without a KV, state in an in-process Map appears to work. You POST a record, the instance holds it in memory, you get a success back. Then the next request lands on a fresh instance, and the record is gone.

The write succeeded. The read succeeded. Nothing errored. That silent version is far worse than an outright failure, because you only find it when someone else is looking.

So the pattern worth copying is: make the app say so. Health returns degraded, with the storage it is actually using and a warning that writes will not persist. The homepage shows a banner until durable storage is configured.

Then two env vars, and that is the whole configuration. KV_REST_API_URL and KV_REST_API_TOKEN.

One more real gotcha. On a shared KV, namespace your keys. Two products both writing an unprefixed posts key silently overwrite each other, and the symptom is missing data, not an error.

Cost: zero to start, genuinely. Vercel free tier plus a free KV tier, or self host the KV for nothing.

Step seven. Three checks, in this order, and none of them is a matter of taste.

First, npm run build. It typechecks every route. That is all it tells you. It tells you the thing compiles.

Second, bash scripts slash verify dot sh with your URL. Eighteen assertions, run against your live deployment. This is the one that is about correctness. The build proves it compiles. This proves it is true on the wire. Only the middle one is about correctness.

Third, the graders. They are the acceptance test, not the build plan. Do not work down a grader's checklist as if it were a roadmap. Run it to find out where you stand.

Say this out loud, because the room needs permission: if you are shipping something at the end of today, stop after the second gate. A product that passes verify dot sh is already further than almost anything on the web.

One trap on the graders. On the Cloudflare one, rescan after every single fix. It reveals sub checks one at a time, so a check that just went green can be hiding the next one underneath it. Three of ours took two or three passes each before they stayed green.
