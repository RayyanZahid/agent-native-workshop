What an AI agent needs five things you can test for

An AI agent needs five things from your site.

Miss one and the agent gets stuck at that step.

Here are the five things an AI agent needs from your site. You can hold your own site up against each one.

Find it. The agent knows only your web address, and from there it can work out everything else your site offers.

Read it. It gets the real content, not just menus and styling.

Get permission. A person says yes once. Nobody has to paste a password or a secret key into a chat.

Use it. The agent can do what a person can do, like book a table or buy a ticket.

Know the cost. It sees the price before it commits, even when the answer is that it is free.

Here is the important part. Miss any one and the agent gets stuck at that step. If it can find you but cannot get permission, it stops. If it gets permission but has nothing to use, it stops.

Most sites I check have one or two of the five and think they are done.

For the developers: the five map to discovery, readability, authentication, a typed callable interface, and pricing metadata.

Part II seven layers, in order

Seven layers to build, and what breaks without each.

Here is the whole middle of the talk on one slide. Seven things to build, in the order I would build them.

Left column is what the thing is. Right column is what goes wrong if you skip it. I have skipped most of these at some point, and every one of them cost me days.

And here is the pattern: none of them fail loudly. Nothing crashes. No error shows up in your logs. The agent just quietly gives up and the person who sent it never comes back.

One. Be findable: small files at standard addresses that say what your site can do. Skip it and agents never learn you exist.

Two. Be readable: everything important is in the page before any code runs. Skip it and agents see a blank page.

Three. Ask permission: the agent asks, and a person says yes. Skip it and people start pasting passwords into chatbots.

Four. Be usable: your list of what you can do is open to everyone. Skip it and agents look, see nothing, and leave.

Five. Talk to other agents: every agent gets its own address. Skip it and a hundred agents behind one address read as one.

Six. Be a good API: clear errors, results in pages, safe retries. Skip it and you have a tidy list of broken buttons.

Seven. Hear about breakages: an address agents can report problems to. Skip it and you find out months later.

For the developers: layer three is RFC 8628, the device authorization grant. Layer six is RFC 9457 problem details, cursor pagination and an Idempotency-Key header. I will name those as we go.

Layer 1 · Be findable the files agents read first

Write it once, or your files stop matching.

  • A dozen small files tell agents what your site can do.
  • You change one and forget another. Now agents are told something false.
  • Nothing breaks loudly. The agent gets an error, gives up, and does not come back.
  • The fix: write it in one place and generate the rest.

First thing to build: be findable.

Your site ends up with about a dozen small files sitting at standard addresses. An agent checks those first to work out what you are and what you can do. Writing them is a boring afternoon.

Keeping them agreeing with each other for six months is the hard part. Here is the shape of it, and I have done this. You give a key one extra permission, and you forget to add that permission to the file that lists them. Now your site is advertising a permission your keys do not actually carry.

Nothing fails loudly. An agent reads the file, asks for that permission, gets a key without it, and the call comes back as an error nobody owns. No crash, no log, nothing in your inbox. It just stops coming back.

So write it in one place and generate the rest. In the kit there is one config file, agent.config.ts, and every one of those eleven files is generated from it. If you can edit the same fact in two places, you eventually will.

For the developers, the eleven are: ai-agent.json, agent-card.json, mcp.json, api-catalog, oauth-protected-resource, oauth-protected-resource slash api slash mcp, oauth-authorization-server, agent-skills index, ai-catalog.json, llms.txt and auth.md. All under /.well-known except the last two.

And one that looks like a duplicate and is not: oauth-protected-resource with the api/mcp path on the end. A strict MCP client that gets a 401 from /api/mcp derives that exact path, per RFC 9728 section 3.1. Ship only the root one and that client gets a 404 and no route to sign in at all. It does not fall back.

  • 403 = I-31 (spoken only now: metadata advertises a permission the minted token lacks, call fails with no error anywhere in the chain)
  • 401 and 404 = F-50 (RFC 9728, OAuth 2.0 Protected Resource Metadata, section 3.1 path insertion; spoken only)
  • 9728 = F-50 · 3.1 = F-50

Layer 2 · Be readable what an agent sees first

Put your contentin the pagefrom the start.

1/5 to 5/5

One change took a scanner score from 1 out of 5 to 5 out of 5.

Many sites send an almost empty page and fill it in with code in your browser. You never notice. Many AI agents read the page before that code runs, so they see nothing.

If you take one idea out of tonight, take this one. Put your content in the page from the start.

Here is what happens on a lot of sites. The page arrives almost empty, and code running in your browser fills it in. You never notice, because your browser runs that code. But many AI agents read the page the moment it arrives, before any code runs. They see the empty version.

We learned this the hard way. We set up our tools inside a React useEffect. We deployed, ran the scanner, and the score did not move. The code only runs in the browser, so the page that came over the wire had nothing in it.

The identical code, moved into a script that the server puts in the page, took that check from one out of five to five out of five. Same code, different place.

To check your own site, fetch the page the way an agent does and look for your content. For the developers: curl -s YOUR_URL | grep -c registerTool. If the count is zero, the agent sees zero, whatever your browser shows you.

Two smaller examples. Our not-found page was the full app, sixty one kilobytes of nothing. We replaced it with under a kilobyte naming the right next addresses, and that check went from one of two to two of two. And if an agent asks for Accept: text/markdown, it wants the substance. Forty kilobytes of HTML is technically valid and practically a refusal.

  • 1/2 to 2/2 = I-33 (agent-friendly 404 check, before and after; spoken only)
  • 61 = I-33 (the 61KB app-shell 404 it replaced, now under 1KB; spoken only)
  • 40 = I-34 (40KB of HTML returned to a request sending Accept: text/markdown; spoken only)

Layer 3 · Ask permission like a valet key

Never paste a password into a chatbot.

  1. 1

    It asks.

    The agent asks your site for access.

  2. 2

    You get a code.

    A short code shows up on your phone.

  3. 3

    You say yes.

    You see what it wants and tap yes.

  4. 4

    It gets a key.

    A key that only does what you approved.

Like a valet key: it starts the car, but does not open the trunk.

Next: ask permission. The rule in one line: never paste a password into a chatbot, and never let an agent hand itself a key.

Think of a valet key. It starts the car, but it does not open the trunk. That is what we want to give an agent: a key that does one limited job.

Four steps. The agent asks your site for access. You get a short code on your phone. You see exactly what it wants, in plain words, and tap yes or no. Then the agent gets a key limited to only what you approved.

Why not just paste a key into the chat? Because anything in the chat can leak to anyone who asks nicely. And a normal sign-in page assumes the agent has a browser and a person watching it. This flow assumes neither.

The limits are fixed when the key is made. There is no way to widen a key after you approved it, because then you would have approved something different from what exists now. If the agent needs more, it asks a person again.

The payoff is a record that reads: a signed-in person approved these five permissions for an agent calling itself X. That survives a security review. "The agent had a key" does not.

For the developers: this is the device authorization grant, RFC 8628. The agent posts to /api/agent/signup/start and gets a short code, then polls /api/agent/signup/poll with the device code. Scopes are frozen at mint time.

Be usable. One rule: show everyone what your site can do, and ask for a login only when something is actually done.

Think of a shop window. Anyone can look in. You only show your card at the till.

Here is what people get wrong. Before an agent signs up, it asks your site what it can do. That question comes with no login. If every tool on your server needs a login, the list comes back empty, and the agent, or a scanner, concludes you have no tools. You built a server and scored zero for it.

So make at least one genuinely useful tool open. Not a stub. A stub is worse, because you advertised something that does nothing.

This deck's own server has eleven tools and eight need no login at all, including one that runs live checks against your own deployed site. You can point it at your site tonight.

For the developers: that is tools/list on remote MCP over streamable HTTP, called with no token. Stdio is not an option in production. It is a local-dev transport and a hosted client cannot reach it at all. If a tutorial handed you a stdio server and told you to deploy it, it was written for your laptop.

Try it during the break: curl -s -X POST YOUR_URL/api/mcp with a JSON-RPC body of method tools/list, and no Authorization header. If you get an empty list back, that is the bug.

Layer 5 · Talk to other agents One address each

Give every agent its own address.

Like everyone having their own phone number.

Only agents with permission can message them.

Talk to other agents. The idea: give every agent its own address.

Picture a company with one shared front desk. Every call goes there, and the caller has to say who they want. Now picture everyone having their own phone number. That is the difference between the two sides of this slide.

The shared front desk works. But it makes every caller say who the message is for, and from outside your whole product looks like one agent, not many. The claim that you have several agents becomes decoration.

With one address each, every agent can be reached directly. Adding another is easy.

Second point: only agents with permission can message them. Leaving it open makes you publicly callable, and that is hard to undo once registries cache you. Open it on purpose or not at all.

For the developers: each agent gets its own endpoint at /api/a2a/agentId, and its own card at that path plus /.well-known/agent-card.json. The cost is one dynamic path segment. A gotcha: supportedInterfaces is required at the card level, not only per skill. I had it on every skill and not on the card, and validation failed with a message that reads like the skills are wrong.

  • 5 = I-60 (layer 5 of the kit's seven layers; spoken only, not on the slide face)
  • 2 = I-61 (the "2" in a2a, the agent to agent protocol name; spoken only)

Layer 6 · Be a good API Where scanner points come from

The biggest win is boring: a good, documented API.

  • AI agents are programs. Programs need a clear, written-down way in.
  • A fancy add-on on a weak API still scores badly.
  • Clear error messages, long lists split into pages, safe to send twice. Only claim them if your API really does them.
  • Speed limits are checked on real replies. Writing them in the docs earns nothing.

Each extra agent file

1 to 2

The special files are the cheap part. They are also the small part.

This is the one I would spend your evening on, because this is where the points are.

The idea is simple. An AI agent is a program, and a program needs a clear, written-down way in. That is an API with a document that describes it.

Look at what a scanner gives for each item. A document describing your API is worth seven points. Data anyone can read with no login is seven. A page for developers is six. Each of those special agent files is worth one or two. So the fun files are the cheap part, and also the small part.

That means a fancy add-on bolted onto a weak API scores badly. The add-on is not the problem. The API under it is.

One surprise. Publishing the description switches on checks that were sleeping. On one real site, the number of usability checks counted went from eighty one to one hundred and fifty after a single document. So expect new red marks to appear. That is fine. You did not break anything. You became clear enough to be graded properly.

For the developers: the error format is RFC nine four five seven, problem plus json, with a remedy field. Results come in pages using cursors. POST requests accept an Idempotency-Key, which is what makes them safe to retry. Those only count if the routes really do it.

And the speed-limit headers, the IETF RateLimit-Limit, RateLimit-Remaining and RateLimit-Reset ones, are checked on live replies. Documentation earns none of them.

Layer 7 · Hear about breakages

Let AI agents tell you when something breaks.

  1. A page moves.

    An agent using it hits an error.

  2. It gives up.

    No email. The person who sent it never comes back.

  3. It tells you.

    A “report a problem” address any agent can use, no login.

A suggestion box by your front door. In our tests, agents filed 18 reports in ours. Let them tell you.

Last one in this part, and it is the cheapest thing on the list.

Here is the situation. You rename a page on your site. Somebody's AI assistant was using that page, and now it hits an error.

It does not email you. It does not file a ticket. It just gives up. And the person who sent it never comes back, and you never hear about any of it.

Things on your site change all the time, and the agents using it are the only ones who find out first. So give them a way to tell you.

When we tested this workshop with AI agents, they sent eighteen problem reports through our own suggestion box, and the count matched what the agents said they sent.

The fix is one address on your site that any agent can send a note to, with no login at all. Think of a suggestion box by your front door. A real note looks like: the page slash pricing is gone.

No login is deliberate, not laziness. The agent that cannot log in to your site is exactly the one with something to report.

For the developers: it is a POST to slash api slash agent slash feedback. Unauthenticated on purpose. Add the route tonight, it is about ten lines.

Here is the scoreboard. A scanner is a free website that looks at your site and gives it a score. Treat the failed checks as a to-do list.

The catch is that two scanners do not measure the same thing. One real site held the top level on Cloudflare's scanner and scored fifty two out of one hundred on ora dot ai, at the same time, for six weeks. So pick one scanner and follow it, because the work is different for each.

The advice: fix what is worth the most first. Do not walk the red list top to bottom, because on a site that is nearly done, most of the list is noise.

And watch the cache between you and the scanner. A file a scanner reads should not be cached for an hour.

Hosting · the quiet trap

Free hosting forgets things without a database.

Free hosting is the right default for this, and it has one sharp edge worth a whole slide.

Free hosting runs your code on a fresh machine for each visit. Say someone saves a note, and your code keeps it in memory. The site says OK. Then the next visit lands on a different machine that never saw that note. You look for it, the site says OK again, and it is empty.

Nothing shows an error. The save worked. The lookup worked. That is worse than a loud failure, because you only find out when somebody else is looking.

The fix has two parts. Connect a small database, which is two settings. And make your site say so when the database is missing. Its status page says degraded, says it is using memory only, and warns that saved data will be lost. The homepage can show a banner until a real database is connected.

One more gotcha. If two projects share one database, give each its own prefix. Otherwise they overwrite each other, and the symptom is missing data, not an error.

Cost: nothing to start. The free hosting plan plus a free database, or run the database yourself.

For the developers: the two settings are KV_REST_API_URL and KV_REST_API_TOKEN, the status route is slash api slash v1 slash health, and the in-memory store is a Map in the function process.

Before we close, one thing we did to this workshop that you can do to your site.

We did not just build it and hope. We ran it on AI agents first. Eleven runs. Each one was a fresh agent on its own empty computer account, and the only thing it got was the one sentence from the start of the talk.

Every single run found the workshop and its seven steps from that sentence. That was the good news. The rest was not as clean, and that is the point.

The agents ran into about twenty five problems. A check script that failed on a plain Ubuntu machine. A checker that dead ended instead of telling them what to do next. We fixed all of them. After the fixes the workshop's agent readiness score went from seventy one to seventy six, and the kit's from sixty eight to seventy four.

Two things we learned about the testing itself. The smaller model, Haiku, only read the rules once we made every entry point say read the skill file first. And with a beginner, Haiku still used jargon, so we shipped ready made plain words in each step instead of hoping it would find them. Sonnet did better on its own.

And the judge needed checking too. We used an AI to grade how well a beginner would follow along, and we had to test that judge against known answers before we trusted its scores.

So the takeaway: test your site with the agents who will use it.
